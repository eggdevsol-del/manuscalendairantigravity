# Artist practice workspace — delivery status

Branch: `codex/tattoi-ivory-design-system`.

## Access

In the authenticated artist app: Settings → Guided walkthroughs → Artist practice workspace (`/practice`). Each artist has an isolated, resumable backend session. Migration `0032_artist_practice.sql` creates only the practice table; Railway runs the additive migration before its existing schema check.

For offline review, run `pnpm practice:preview` and open `output/tattoi-artist-practice/index.html`. The preview uses the same transitions and React workspace, stores only its own progress, and prohibits network connections with Content Security Policy.

## Delivered

Twenty-two guided workflow chapters cover enquiry, consultation, references/design brief, booking wizard, deposit, full-day sitting, forms/procedure, final payment, large projects, rescheduling and promotional repricing, promotions, calendar-fill audiences and expiry, vouchers, Today, clients, messages, availability, waitlist, finances, bank, profile, imports, supplies, shopfront, studio and settings.

“Practise with app controls” opens the actual artist screens using a closed mock tRPC adapter and a separate query cache. Every currently rendered control is available to the action guide; conditional sheets are scanned when opened, with the guide kept inside the active sheet's focus trap. Input, navigation, review and successful mutation progress is saved per artist. Controls can be highlighted, replayed and revisited. The source inventory is generated by `pnpm practice:audit` and rejects unmapped endpoints in the reachable artist screen graph. Shared components contain some client/supplier exports; these are classified separately rather than counted as artist tutorials.

Connected mock records flow between the real wizard, Messages, project, forms, calendar, payments, cart, orders and settings. Scheduling and offer maths reuse production engines. References share bundled artwork between Messages and Design & references. Payment, refund, stock, studio permissions, duplicate imports, notification recovery and client acceptance/decline have simulated outcomes. Provider-facing controls explain or simulate the handoff: they do not send SMS/push, import a real store, upload files, charge cards, connect a bank or change billing. Deprecated endpoints with no current artist UI are not exposed as new features.

The backend validates ownership and revisions, locks updates transactionally and writes only `artist_practice_sessions`. Unknown adapter operations fail closed. Practice skips live authentication persistence, notification SDKs, external redirects, production query invalidation and account deletion effects. Cart storage is confined to practice state. Reset/back/checkpoints and completion survive chapter changes.

Bank & payouts in the real app now opens embedded Stripe onboarding for existing Standard, Express and Custom accounts and new accounts without replacing existing accounts. Stripe authentication is preserved where required, with retry and explicit hosted fallback if embedded loading fails.

## Validation

Focused lifecycle, ownership/isolation, UI, real-screen adapter, bank/Stripe, checkout, guide and scheduling tests: **145 passed across 18 files**. TypeScript passed. Production bundle, PWA and offline preview are checked before push. Deployment/migration confirmation is recorded separately after Railway completes.

The local file preview could not be inspected in the browser because its URL was blocked by browser policy. Component tests render all connected artist screens, but this does not constitute a visual browser sign-off. Real SMS delivery, real Stripe verification and purchases remain outside fictional practice testing.
